# Contributing and requesting changes

This repository hosts multiple REAPER tools. Reports, ideas, tests, documentation and code
contributions are welcome. Search existing issues and discussions before opening a new topic.

## Choose the right place

| Situation | Where to post |
|---|---|
| Something does not work as expected | A **bug issue** |
| An idea, workflow need or design question still needs exploration | A discussion in **Ideas** |
| A feature or change request has defined behaviour and completion criteria | An **enhancement issue** |

Discussions help us decide what to build; issues track defined work. A precise request can go
straight to an issue: a discussion is not mandatory. Requests that still need design work may
be redirected to Ideas. Implementation issues should link to the relevant discussion, if any.

- Issues: https://github.com/solyarisoftware/reaper/issues
- Ideas: https://github.com/solyarisoftware/reaper/discussions/categories/ideas

## Identify the tool

Start the title with the tool name, for example `CCScope - Unexpected value after Clear`.
The maintainer applies labels such as `plugin:ccscope`, `bug` and `enhancement`; contributors
are not expected to have permission to manage labels. The Ideas category describes an
exploratory stage; the enhancement label does not imply an implementation commitment.

## Report a bug

Include:

- the tool and its version, REAPER version and operating system;
- steps to reproduce, expected behaviour and actual behaviour;
- relevant settings and MIDI input conditions, including device, CC and channel when applicable;
- a minimal example, screenshot or observations when useful.

Remove personal information and credentials from attachments. A screenshot helps, but does not
replace reproduction steps. If the cause is uncertain, describe the observation rather than
assuming a hardware or software fault.

## Propose an idea or a defined change

For an **idea**, explain the workflow, the problem and why solving it would help. Alternatives,
examples and test data are welcome; an implementation design is not required.

For a **defined change request**, describe the requested behaviour, motivation, scope and
observable criteria for completion. Mention compatibility concerns and link related topics.

An open discussion or issue does not guarantee acceptance, implementation, priority or a delivery
date. Scope and priorities remain the maintainer's decision.

## Contribute improvements

Testing, reproducible examples, documentation and code are all useful contributions. Discuss
substantial changes before starting implementation to avoid work on an approach that cannot be
accepted. Keep pull requests focused, explain the change and report what was tested. Never
include credentials or personal configuration. The ReaPack `index.xml` is generated by CI and
must not be edited by hand.

### Where the CCScope code lives

One conductor, leaf panels and reusable utilities. `ccscope.jsfx` declares the host state and
every slider and owns the `@gfx` pipeline, which calls the panels and overlays in order:

| file | owns |
|---|---|
| `ccscope.jsfx` | state, sliders, MIDI ingest, the frame pipeline, the control-bar adapter |
| `ccscope_utils.jsfx-inc` | the `mem[]` address space and the (CC, channel) data |
| `ccscope_metrics.jsfx-inc` | the one-second metrics |
| `ccscope_layout.jsfx-inc` | frame geometry and the metric columns |
| `ccscope_plot.jsfx-inc` | time window, grid, image cache, traces |
| `ccscope_rows.jsfx-inc` | bars, metric fields, hovered reading cache and row/metric-help content |
| `ccscope_status.jsfx-inc` | the line at the bottom |
| `ccscope_controlbar.jsfx-inc` | the cells, their lists and the pointer |
| `ccscope_tooltip.jsfx-inc` | reusable wrapping, fitting and opaque tooltip painting; no metric vocabulary |

Two rules keep it that way, and both are checked by `tests/test_ccscope_tools.py`: **a panel
calls no other panel** (the pipeline orders them, so a new panel or a third rows mode touches
one file), and **the control bar knows no parameter** — it receives values and texts and returns
a list of changes, so another effect can copy that file and use it with its own vocabulary.
The conductor coordinates row/metric dwell and menu suppression, then calls the tooltip renderer.
No panel calls the renderer or another panel. Rows cache only the hovered cell while drawing; help never recalculates metrics.
The renderer reserves four live-reading lines, measures invariant full/compact bodies and restores
the caller's font and drawing state. It allocates no `mem[]` ranges.
Every include opens with what it owns, reads and writes. EEL2 has no forward declarations: a
function may only call what was declared before it, so the order inside a file is the
dependency order, and `@provides` in `ccscope.jsfx` is the single list of package files — the
probes read it, ReaPack reads it, and a forgotten entry is a plugin that will not load.

## Documentation conventions

Each package keeps its user documentation next to its sources, and it is written for the person
using the plugin, not for the person reading the code:

- **`README.md` is the product page.** What the tool does, how to install it, what the numbers
  mean, where to report something. Measurements, memory layouts and pixel coordinates belong in
  the commit that introduced them, in `CHANGELOG.md`, or in the linked issue — not on the front
  page.
- **`CHANGELOG.md` is one line per change**, written as the effect a user notices, with a link to
  the issue or discussion that holds the reasoning. Notable changes only.
- **The roadmap lives in issues and discussions, not in a file.** `bug` issues for defects,
  `enhancement` issues for defined work with completion criteria, Discussions in **Ideas** for
  what is still being designed. A `TODO.md` next to a package duplicates that and then drifts
  out of date; it is not kept.
- **The `@about` header in the package source is the description ReaPack displays**, so it
  follows the same rule as the README: what it does for the user, not how it is implemented.
- **The `@changelog` header holds the current version only.** ReaPack displays whatever the block
  contains, so a full history kept there is displayed in full under every release;
  `reapack-index` preserves previous versions' changelogs on its own. The history belongs in
  `CHANGELOG.md`, which ReaPack does not publish.

## Optional support

If these tools are useful to you, you can optionally support their maintenance and development
through the donation links in the repository README:
https://github.com/solyarisoftware/reaper#support

Contributions help cover the time and costs involved in investigating requests, implementing
changes, testing and documentation.

Donations are entirely voluntary. You do not need to donate to report a bug, suggest an
improvement or contribute to a discussion. A donation does not guarantee implementation,
priority, a delivery date or support in exchange. It is not a purchase and does not change
the software license or unlock features.
